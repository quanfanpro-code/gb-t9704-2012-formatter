# 普通公文安全修复与发布需求

## 一、目标

将程序收敛为可靠的 GB/T 9704—2012 一般普通公文排版工具。修复无法启动、内容损坏、错误合规结论和输出覆盖等高风险问题；迁移到 .NET 10；补齐自动化测试、README 和发布验证；最后将同一版本同步到两个本地目录并推送远端仓库。

## 二、本轮支持范围

1. 只支持一般普通公文。
2. 暂时下线信函、命令、纪要模式，不保留仅有名称而没有专属规则的入口。
3. 不处理上行文。发文字号按一般公文规则居中；需要上行文版式时由用户手工调整。
4. 页眉原样保留。
5. 各节页脚统一改为 GB/T 9704—2012 规定的页码样式，不沿用原页脚内容。
6. 公式、批注、修订、脚注、尾注、文本框、嵌入对象等复杂内容必须保留。程序跳过其所在段落的高风险改写，并在检查报告中提示人工确认。

## 三、必须修复的问题

### 3.1 程序可用性

- 清除对已不存在图标资源的引用，确保程序窗口能正常启动。
- 主程序和测试项目迁移到 `net10.0-windows`。
- 将 WPF-UI 升级到 4.3.0，将 DocumentFormat.OpenXml 升级到 3.5.1。

### 3.2 内容安全

- 不得改变正文、表格中的文字和数字含义。
- 不得把纯数字改成金额格式，也不得自动补千分位或小数位。
- 不得删除表格尾部空行、空列、图片、对象或占位结构。
- 不得把换行、分页、制表符、编号、公式、脚注、尾注、修订、批注、文本框和嵌入对象压平成纯文本。
- 排版操作只调整明确需要的版式属性；遇到结构复杂或判断不可靠的段落时跳过并提示。

### 3.3 国标业务规则

- 机关标志、发文字号、公文标题和正文必须按其在文档中的真实位置识别，不能仅凭“居中”判断标题。
- 一般公文发文字号居中。
- 页码使用国标要求的宋体四号半角阿拉伯数字和一字线形式，并覆盖各节旧页脚。
- 对无法可靠识别的公文要素，程序不得假装已经正确处理，应在报告中列为人工确认事项。

### 3.4 检查报告可信度

- 必须检查最终输出文件，而不是只检查排版前的输入文件。
- OpenXML 结构校验错误属于阻断错误，不得给出“通过”。
- 报告只列出实际执行的检查，不得把未检查规则写成已检查。
- 页码、标题、发文字号等结论必须反映最终输出文件的真实状态。
- 存在阻断错误时不得发布为正常结果；存在复杂内容或无法可靠判断的规则时标记“需要人工确认”。

### 3.5 文件安全

- 不覆盖已有输出文件。
- 输出文件名冲突时生成新的唯一名称。
- 采用临时文件完成排版和校验，只有校验通过后才发布为正式输出。
- 失败时保留可追查信息，不删除或覆盖用户原文件。
- 批量检查报告在源目录不可写时，应保存到可写的输出位置，不能使整个批处理无故失败。

## 四、测试与验收

### 4.1 自动化测试

至少覆盖以下场景：

- 主窗口所引用的本地资源全部存在，程序可正常启动。
- 机关标志、发文字号、标题和正文不会互相误判。
- 表格文字、数字、行列、图片及对象保持不变。
- 段落换行、分页、制表符、编号和复杂对象保持不变。
- 有效的 OpenXML 输入仍产生有效输出。
- 结构校验错误会阻断“通过”结论。
- 检查报告使用最终输出结果。
- 页眉保留，旧页脚被标准页码替换。
- 同名输出不会被覆盖。
- 信函、命令、纪要不再出现在可选模式中。

### 4.2 发布验证

- Release 构建零错误。
- 全部自动化测试通过。
- 代码格式检查通过。
- 依赖漏洞检查通过。
- 实际启动程序，确认主窗口出现且没有未处理异常。
- 使用代表性 DOCX 样本完成端到端排版，核对内容保持、国标页码、OpenXML 有效性和报告结论。
- README 准确说明支持范围、使用方法、输出规则、限制和人工复核事项。
