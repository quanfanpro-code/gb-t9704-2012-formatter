# 普通材料版式回归修复需求

## 背景与问题

程序处理 `成都轨道交通集团_问题二回复.docx` 后，文字和表格数量未丢失，但成稿从 8 页膨胀到 13 页，并出现明显的版式割裂：

1. 多行标题未被识别为标题，被按正文设置为三号仿宋、首行缩进和两端对齐，导致标题字符异常拉伸。
2. 含超链接的两个段落被整体跳过，仍保持原稿小四宋体，与三号正文不一致。
3. 六张表格未执行任何格式化，字号、行距和对齐方式与正文不协调。
4. 最终检查只验证文件结构、字体是否安装和页面参数，没有验证标题、正文、复杂段落及表格是否真正完成排版。

上述回归主要来自提交 `fcc6672`：标题识别开始依赖文号，复杂段落在格式化前直接跳过，表格格式化器被改为空实现。

## 用户与使用场景

使用者在 Windows 桌面程序中选择普通材料模式，对包含多行标题、正文、超链接和表格的 DOCX 文件执行 GB/T 9704—2012 参照排版，并直接使用程序生成的成稿。

## 功能范围

1. 没有标准公文文号时，仍能依据首段位置、标题样式、多行结构和标题文本识别标题区。
2. 本类多行标题统一使用二号方正小标宋简体，各行居中，不保留用于人工定位的空格、首行缩进或两端对齐。
3. 含超链接、书签、批注、域、图片等复杂结构的段落必须保留原结构和目标关系。
4. 在不删除复杂结构的前提下，统一复杂段落中可安全处理的可见文字字体、字号、行距、缩进和对齐方式。
5. 表格保留原有文字、数字、行列、合并关系、宽度、图片和对象；可见文字统一为小四号仿宋，设置固定行距、垂直居中和合理对齐。
6. 最终检查增加版式结果校验，验证已识别标题、普通正文、复杂段落可见文字和表格文字符合本次规则。
7. 最终检查属于兜底断言。程序必须先自动完成排版，不得用“阻断”“警告”或“人工复核”代替可以自动完成的格式修复。
8. 审计 JSON 应准确记录已执行的版式检查及结果，不再仅凭 OpenXML 结构合法就认为排版流程有效。

## 明确不做

1. 不修改文档业务文字、数字、超链接地址或表格数据。
2. 不删除批注、书签、域、图片、嵌入对象或其他复杂结构。
3. 不重做全部公文文种体系，不扩展上行文、联合行文、信函、命令或纪要专属格式。
4. 不引入新依赖，不改桌面界面，不改变输出文件命名规则。
5. 不覆盖原稿和现有输出文件。

## 约束与风险

1. 必须使用 Open XML 原位调整属性，避免通过重建段落或单元格造成内容及关系丢失。
2. 表格只调整安全的显示属性，不解释或重新格式化业务数字。
3. 图片、对象和域本体保持不动；仅处理其所在段落及普通文字运行。
4. 修改现有文件前按用户规则备份到 `C:\Users\27651\BackUp\gb-t9704-2012-formatter_年月日_时分秒\`。
5. 修复后必须使用 Microsoft Word 原生渲染核验实际页数和视觉效果，不能只依赖 OpenXML Schema。

## 验收标准

1. 回归样本首段被识别为标题区，使用二号方正小标宋简体、居中、无首行缩进、无两端拉伸。
2. 两个含超链接的段落保留全部超链接及地址，可见正文统一为三号仿宋并采用正文段落格式。
3. 六张表格的文字和数字逐项保持不变，行列数、合并关系和宽度保持不变；可见文字统一为小四号仿宋。
4. 原稿与成稿的正文文字、表格文字、超链接数量和目标地址完全一致。
5. 成稿不存在正文三号与遗留小四号混排的异常；允许表格按明确规则使用小四号。
6. 新增回归测试在修复前失败、修复后通过，并覆盖无文号多行标题、复杂段落和表格三个根因。
7. 全部现有自动测试、Release 构建和格式检查通过。
8. 使用 Word 原生渲染复核真实样本；标题正常、复杂段落无字号断层、表格可读，页数变化与三号正文排版相符。
9. 审计 JSON 明确包含版式一致性检查记录，检查结果与实际输出一致。
